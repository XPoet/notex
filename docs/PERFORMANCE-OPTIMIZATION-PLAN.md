# NoteX 架构与性能优化方案

方案日期：2026-11-01。审查基线：`1e49d92`，`package.json` 版本 `0.0.17`。

状态：四批整改的本地实现、全量质量检查和 macOS 原生 Debug 构建已完成。本文保留整改前审查证据，并在文末记录实现与验证；macOS 发行版 WKWebView 的实机性能验收仍待执行。

用户反馈：单篇正文较长时输入不流畅，内容较多时滚动和切换存在轻微卡顿。

## 判断

现有 Tauri 2 + Vue 3 + CodeMirror 6 + Rust + SQLite 适合纯本地笔记应用。Command → Service → Repository 的分层方向、SQLite WAL、阻塞任务转移到后台，以及普通笔记列表的虚拟化均有实际实现。当前证据支持保留技术栈并整改数据处理粒度。

主要问题是：编辑路径多轮全文工作；保存和选择后重新读取整个列表；单篇元数据修改触发全库索引重建；草稿保存与导航缺少统一边界。

原审查阶段未修改项目业务代码、依赖或锁文件，未读取用户笔记数据库，未读取或分析依赖和构建输出目录。浏览器验证使用临时挂载的真实组件与合成正文；数据库验证使用内存数据库。本方案保存于项目 `docs/` 目录，供后续实施和验收使用。

## 按优先级排序的发现

### 1. P1：导航可覆盖未保存草稿

- [WorkbenchView.vue:109](../src/views/WorkbenchView.vue#L109) 中分类、标签、目标笔记参数变化时直接加载；只有 create 分支预先 flush。
- [notes.ts:48](../src/stores/notes.ts#L48) 将列表加载与默认选中第一篇绑定，直接替换 selectedNote，没有保存原草稿。
- [useAutoSave.ts:39](../src/composables/useAutoSave.ts#L39) 卸载时仅取消计时器；路由未设置统一的离开保存守卫。应用关闭流程已有循环 flush，但页面导航未复用同等保障。

直接执行当前 store 源码、替换 Ref/store factory 和 IPC 后，已复现：load(A) → updateDraft(A 的新正文) → loadByCategory(B)，当前内容变成 B，isDirty 仍为 true，而 saveNote 调用为 0；再 flush 只保存 B 的旧内容，A 的改动已经被覆盖。此验证覆盖状态机，不包括真实 Vue 调度。

整改：统一分类切换、选笔记、离开工作台入口，在替换编辑会话前保存当前 revision；保存期间发生的新编辑必须继续保存或保留为该笔记草稿。加载请求使用序号，丢弃旧请求的迟到结果。不要仅加固定延时。

### 2. P1：状态栏每次编辑做多轮全文扫描

[EditorStatusBar.vue:17](../src/features/editor/EditorStatusBar.vue#L17) 每次正文变化都执行中文 match、中文 replace、英文 match、去空白后 Array.from、全文 split。产生多个与正文规模有关的字符串和数组。

整改：先把统计更新节流至约 150–300 ms，并合并统计遍历；行数使用 CodeMirror 文档元数据。后续根据变更范围维护统计。统计显示不应成为每次输入必须同步完成的工作。

### 3. P1：全文快照撤销历史与多次全文序列化

[MarkdownEditor.vue:35](../src/features/editor/MarkdownEditor.vue#L35) 的 string[] 历史没有上限；[同文件:166](../src/features/editor/MarkdownEditor.vue#L166) 每次正文事务将当前文档 toString 两次、旧文档 toString 一次，并保留整篇旧正文；props 回流时又全文比较。撤销通过替换整篇文档实现。

整改：使用 CodeMirror 的变更历史机制，合并相邻编辑；至少先限制自建历史的内存预算并消除同事务重复序列化。进一步将编辑器即时文档与持久化快照分离，保存、导出、离开前读取快照。不能只延迟 v-model 而不调整强制保存，否则会保存旧内容。

当前直接依赖只有 @codemirror/state 和 @codemirror/view；采用 @codemirror/commands 历史扩展前须按项目规则评估依赖变更。本次未添加依赖。历史、事务变化与装饰映射能力见 [CodeMirror 官方参考](https://codemirror.net/docs/ref/)。

代码可以证明持有每个事务的逻辑全文快照；实际字符串存储共享、堆内存与垃圾回收停顿需要 heap profile，不能简单按每键必然复制三份物理内存计算。

### 4. P1：保存与选择都刷新全量列表，后端列表读取完整正文

[notes.ts:115](../src/stores/notes.ts#L115) 每次保存后 refreshNotes；[同文件:129](../src/stores/notes.ts#L129) 切换依次等待 flush、空笔记清理、详情读取和全量列表刷新。

[Rust notes repository:55](../src-tauri/src/repositories/notes.rs#L55) 没有分页，SELECT 包含 content，Rust 为每篇读取完整正文后只返回摘要。分类、标签列表采用相同模式。摘要响应虽小，数据库读取及分配成本仍随总正文体积增长。

从全局搜索打开目标笔记时，工作台先加载列表并选第一篇，再选择目标并刷新列表；目标不是第一篇时出现两次列表获取和两次详情获取。

整改：保存返回确认信息与最新摘要，局部更新当前条目；普通切换只读取目标详情。清理空笔记返回是否实际移除，按结果调整本地列表。新增 Migration 维护摘要字段，使列表查询不取正文；为普通、分类、标签列表统一分页/游标契约。分页后需同时调整搜索与定位目标笔记逻辑，避免只搜索当前页。

现有 [NoteList.vue:29](../src/features/notes/NoteList.vue#L29) 已有固定行高虚拟化，应保留。瓶颈不等于未做虚拟滚动。

保存队列还会保留重复 revision 的待保存任务，建议按笔记和版本合并。保存成功但随后列表刷新失败时，当前代码仍报告保存失败，应区分持久化失败与界面刷新失败。

### 5. P1：单篇分类/标签更新触发全库索引重建

[CategoriesService:94](../src-tauri/src/services/categories.rs#L94) 和 [TagsService:65](../src-tauri/src/services/tags.rs#L65) 先提交业务更新，再 rebuild_index。新建空分类、空标签也全量重建。

[SearchRepository:19](../src-tauri/src/repositories/search.rs#L19) 在一个事务内收集全部正文、删除全部索引并重新分词插入，造成与全库正文规模相关的 CPU、内存和写锁开销。业务更新与索引更新分为两个事务，索引失败时业务数据已经提交。

整改：单篇变化只刷新该篇；分类重命名/移动只更新受影响笔记；新建空分类/标签不刷新。将业务变更和索引维护放在同一事务。Service 负责事务范围，Repository 提供接收事务的 SQL 方法，避免跨仓储各自提交。

这也偏离了 [技术设计:186](../docs/TECHNICAL-DESIGN.md#L186) 的增量维护要求。

### 6. P2：图片引用每次编辑独立扫描两遍并全量重建装饰

[imagePreviews.ts:63](../src/features/editor/imagePreviews.ts#L63) 每次 docChanged 全文提取引用并重建全部装饰；[useNoteImages.ts:46](../src/composables/useNoteImages.ts#L46) 又进行一遍全文解析。没有图片的长文也承担扫描。

整改：共享图片引用解析结果；保留装饰映射并按变更更新。代码围栏可能跨行，不能只重扫一行就声称语义等价。图片读取目前按全部引用立即启动，需限制并发、视口附近优先加载，并采用缩略图与有总字节预算的缓存。

### 7. P2：索引定位、启动重建与分词仍有可量化退化

[V003:1](../src-tauri/migrations/V003__add_note_search.sql#L1) 把 note_id 设为 UNINDEXED，而 [SearchRepository:53](../src-tauri/src/repositories/search.rs#L53) 按该列删除。用内存 SQLite 3.51.2 复刻 schema，查询计划确认 note_id 扫描；每行 search_text 为 1020 ASCII 字符，7 次中位数如下。

| 索引行数 | 按 note_id 删除 | 按 rowid 删除 |
| -------- | --------------: | ------------: |
| 1,000    |        0.142 ms |      0.010 ms |
| 10,000   |        1.486 ms |      0.031 ms |
| 50,000   |        7.468 ms |      0.036 ms |

证明复杂度退化，但该实验的绝对耗时不能单独解释当前卡顿。建议通过新增 Migration 建立稳定的整数文档 ID 与 FTS rowid 映射，按 rowid 定点维护；不能对 FTS 虚拟表直接添加普通索引。

[BootstrapService:25](../src-tauri/src/services/bootstrap.rs#L25) 正常启动也无条件重建全库。应按索引版本、恢复变化和持久化 dirty 标记决定是否修复。

[分词函数:262](../src-tauri/src/repositories/search.rs#L262) 对每个汉字创建 String，再收集并 join。提取原函数使用 rustc -O 独立运行，5 次中位数：1000 汉字 0.060 ms，10 万汉字 6.363 ms，100 万汉字 73.417 ms。仅为后台分词 CPU，不包含 SQL/IPC/磁盘。可改为流式写入 String，减少小对象分配。

### 8. P2：搜索分页存在旧请求遗留加载状态

[search store:17](../src/stores/search.ts#L17) 新查询没有复位 isLoadingMore，而旧分页响应因 requestVersion 不匹配，不再清理它。已直接执行当前状态机复现：旧 loadNext 挂起 → 新 search 成功 → 旧页返回，isLoadingMore 仍为 true；之后 loadNext 被 guard 拦截，用户会看到持续加载或无法继续加载。

整改：新查询初始化独立分页状态，用分页请求令牌管理归属。搜索结果组件对累计已加载结果仍全量渲染，连续加载很多页后需虚拟化或分页显示。左侧列表即时搜索也会每键扫描全部摘要，建议去抖并缓存规范化检索文本。

## 建议实施顺序

| 批次 | 工作                                                         | 验收重点                                                |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------- |
| 1    | 导航保存屏障、请求归属、统计节流、重复全文转换、撤销历史预算 | 快速切换不丢草稿；长文输入耗时降低；历史内存受控        |

不建议先更换数据库、前端框架、编辑器或引入庞大连接池。每次操作重新开数据库连接值得后续测量，但目前收益证据弱于上述全量工作，应后置。

## 建议性能与正确性验收

- 在目标 macOS 发行版的 WKWebView 上建立基线；开发 Chromium 数据只用于定位和对照。
- 正文覆盖 1 万、10 万、50 万、100 万字符；组合中文、Markdown、多行、超长单行、代码围栏和图片。
- 笔记数量覆盖 100、1000、10000，同时控制总正文体积，避免所有大规模测试都使用十余字短正文。
- 分别测输入到绘制、持续滚动、切换详情、自动保存、分类/标签修改和启动，报告 P50/P95、长任务、堆内存、IPC 次数和 SQL 耗时。
- 建议先以 10 万字符正文建立性能验收门槛：输入到绘制 P95 小于 16.7 ms、无超过 50 ms 的编辑主线程长任务；50 万以上单独定义长文档预算。此为建议目标，尚未证明达成；允许保存的正文长度上限不等于流畅性承诺。
- 保存前后快速导航、保存中继续输入、乱序加载返回、旧搜索分页返回必须有回归测试。
- 必须观察保存和分类/标签变更同时发生时的性能，不能只测静止页面。

### 关键实现约定

- 编辑器保持同步 `v-model`，保存屏障拿到当前正文；不会通过延迟正文同步来换取较低输入耗时。
- 撤销历史使用现有 `@codemirror/state` 的 ChangeSet，保留变更文本及前后选择，不新增依赖。历史最多 200 组、4 MiB 估算预算；普通相邻输入在 500 ms 内合组，一组最多 100 个事务。IME 使用独立组合输入分组。预算是变更文本和元信息估算，不等于 JavaScript 堆内存实测。
- 状态栏每 200 ms 最多更新一次，统计单次遍历，不构造逐字符数组；普通输入的共享图片引用解析最多每 160 ms 一次，结构变化及时重算以保持跨行代码围栏语义。
- 列表默认每页 50 条、最多 100 条，摘要与总数在同一数据库读取事务内取得。普通选择不刷新列表，普通保存局部更新；标题排序、活动检索、页外笔记保存、置顶和结构变化复位有界页，分页追加按 ID 去重。
- 列表搜索沿用 250 ms 防抖，后端检索标题与持久摘要，不局限当前已加载页。全文搜索仍由 FTS 接口负责。
- 新增 V004，旧 Migration 保持不变。升级事务统一回填摘要、建立文档 ID 映射、重建索引并写入版本；失败回滚到旧结构和原始内容。
- 分类、标签与回收站更新、对应索引维护在同一事务内提交。新增空分类/标签不刷新索引，正常启动不全量重建。
